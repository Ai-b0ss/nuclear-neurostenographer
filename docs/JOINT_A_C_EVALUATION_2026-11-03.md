# Независимая оценка joint A+C: MOSS / VibeVoice против GigaAM + диаризация

**Дата:** 03.11.2026. **Статус:** исследовательское поручение / NOT_RUN. Это **не** подтверждённая победа joint-моделей и **не** просьба заменить конкурсный APK. Контекст: [CONTEXT_RECAP_2026-11-03.md](CONTEXT_RECAP_2026-11-03.md).

## 1. Почему эта работа обязательна для честного выбора архитектуры

Тимлид предлагал не только сменные A (ASR), B (verification), C (diarization) над общим Core, но и сравнение с системой, где **одна модель сразу выводит текст, идентификаторы говорящих и времена**. Это альтернативная архитектура, не дополнительная игрушка.

Существующая modular baseline: PCM → A0 GigaAM v3 CTC + C0 pyannote/ERes2Net или исследовательский C2 Nemotron INT8 → осторожное сопоставление фраз → TXT/JSON/SRT. Преимущество modular: независимые замены, fallback и интерпретируемая ошибка. Недостаток: ошибки совмещения окон/спикеров и вероятность потери контекста.

Joint: PCM → MOSS или VibeVoice → структурированные интервалы, speaker IDs, текст → тот же Core/UI/export. Потенциальное преимущество: одна модель совместно учитывает звук/слова/говорящих, меньше склеек. Риски: генеративные вставки, сдвиг времени, нестабильные IDs, сложный Android runtime и высокое потребление памяти. Эти плюсы/минусы — гипотезы, их надо измерить.

Ситуация на 03.11: **MOSS и VibeVoice внесены в карту исследований, но репозиторий не содержит закрытого сопоставимого бенчмарка этих моделей с A0+C0/C2 и не было назначено отдельного ответственного**. Работы Sonnet по Android и Opus по C2 не заменяют этот эксперимент. Не ждать полного завершения APK: исследования могут идти параллельно на ПК/в отдельной ветке.

## 3. Воспроизводимый Gate 0 — ПК без изменения конкурсной ветки

1. Создать независимую исследовательскую ветку/worktree, **не менять** feature/long-recordings, main, research/nemotron-android, уже исполняемые CI и модели по умолчанию.
2. Проверить model card и официальный пример запуска, тип лицензии весов и inference-кода, право локального использования и скачивания; зафиксировать exact commit/revision, SHA-256 и конфигурацию, версию Python/runtime, зависимости, GPU/CPU. Не применять удалённый API и не отправлять закрытое аудио.
3. Подготовить один immutable список test files с SHA-256 исходного WAV, sample rate, длительностью, каналами, референсным транскриптом, эталоном активности и говорящих, классом сложности и явной лицензией. Никакого отбора файлов *по результатам* моделей.
4. Запустить A0+C0 и A0+C2 как две modular-baseline, затем MOSS 0.9B и VibeVoice-ASR-Streaming-1.5B **на том же аудио**, без необъявленной нормализации и подгонки. Если среда/runtime различаются, качество можно сравнивать, а RTF/PSS — только с явно описанными устройствами и ограничениями. Измерять полный wall time, не только время одного энкодера; отдельно cold load/inference/postprocessing.
5. Привести выводы всех кандидатов к схеме {start_ms, end_ms, speaker_id|null, text, provenance, optional confidence}. Факт отсутствующих confidence/word timestamps не заменять интерполяцией. Отдельно проверять наличие выдуманных слов на тишине, неверное число говорящих и возвращение A–B–A.
6. Получить компактные JSON/CSV итогов и per-case failure table с версией scorers. Не публиковать аудио, приватные тексты, raw credential/config. Пустой файл, ошибка, timeout, OOM = FAIL/полное пустое предположение по документированному правилу, а не скрытое исключение из знаменателя.
7. Результат: один Markdown verdict на **тех же** записях, со ссылками на frozen corpus manifest, scores, runtime, stdout/stderr и замечания о license/ARM feasibility. Не делать merge в конкурсную ветку без измеренного выигрыша и ARM64 acceptance.

## 4. Набор данных и протокол

- **DEV/R:** размеченные короткие клипы 1–4 голоса, A–B–A, 2–3/4 голоса, шума 0/10 dB, паузы/тишина/не речь, длинные 5–20 минут; можно использовать synthetic-speech-diarization-ru, ru-book-mix-10h после проверки аудио/эталонов/прав. Эти наборы не считать автоматически честным тестом естественного общения.
- **NATURAL:** настоящие русские 2-канальные разговоры (например DataHive sample) при наличии законного доступа. Исходная VAD-разметка по каналам может быть **псевдоэталоном**, но не человеком размеченным RTTM. Для natural DER/cpWER нужна независимая разметка слов, границ, спикеров.
- **LOCKED HOLDOUT L:** собственная 2–4-голосая запись команды (добровольное согласие, хранение локально, без доступа моделям при настройке), короткие междометия, перебивание, разные расстояния до микрофона, разные типы речи, шум. Заморозить список и эталоны до финального выбора, не тюнить по L.
- **STRESS S:** 20-минутная запись или зацикленный публичный материал; отдельно проверять память, OOM, длительное RTF, состояние процесса. Stress не является оценкой точности слов и голоса.

Для каждой модели:
- **WER** (нормализация русского строго общая, фиксировать правила ё/е, цифры, пунктуацию).
- **cpWER** (слова с разнесением по говорящим; неизвестные говорящие учитываются явно).
- **DER** (collar = 0 и 250 мс, оба режима с overlap и без него; есть только при независимой валидной time/speaker разметке). Отдельно missed speech / false alarms / confusion и ошибка числа голосов.
- **Overlap-specific cpWER**, 2/3/4 speaker, A–B–A, false words на тишине/музыке/шуме, timed drift на длинных записях.
- **RTF** = полный wall time / длительность исходного файла. Разделять холодную загрузку, inference, postprocess; одинаковые CPU thread counts и precision, иначе прямо отметить несопоставимость.
- **PSS/RSS**, суммарно одновременно по app и worker там, где они есть; размеры файлов/диска, failure/timeout и повторяемость. На Android отдельно ABI, airplane mode, стабильность 5 повторов, температура и расход батареи.

Маленький набор годится для первичного отсечения грубых проблем, не для заявления «лучшая в России». Для статистически значимых утверждений нужны парные сравнения по файлам, доверительные интервалы/пермутационные проверки и достаточное число независимых разговоров; единые thresholds не подгонять на locked holdout.

## 5. Gate 1: переносимость, но только после качества

Доказанное улучшение на ПК — лишь кандидат на порт. Проверить:
- поддержка ops и лицензии конкретной quantized модели и inference runtime;
- CPU-only baseline, тип kernel, ARM64 NEON/NNAPI/LiteRT/MNN/NCNN, если реально есть код, а не маркетинговая метка;
- модель/активации в физической свободной RAM, без OOM/lowmemorykiller, 16 KB ELF/ABI, отсутствие сети, воспроизводимая загрузка проверенных весов;
- cold/warm RTF, 5 повторов, разные Android, microphone→inference→TXT/SRT/JSON и fallback;
- что в APK не попали запрещённые TTS/GPL native зависимости, публичный APK не раздавать без notice/legal review.

В отличие от standalone A, joint не может автоматически использовать speaker turns и текстовый decoder от текущих Kotlin адаптеров. Для интеграции потребуется только маленький **adapter Core** и проверка структуры output, а не переписывание UI/экспорта или выдуманные word timestamps.

## 6. Решение и ответственность

**Рекомендованная исследовательская очередь:** MOSS 0.9B сначала (относительно компактная модель с официальной single-pass постановкой), VibeVoice-ASR-Streaming 1.5B затем; это **порядок проверки**, не предсказание победителя. Ведомый критерий — честная качество/операционная стоимость, а не количество моделей.

**Предлагаемый владелец:** отдельный Speech ML/C++ разработчик с доступом к ПК/GPU, НЕ Sonnet, который закрывает физический продукт, и НЕ Opus до завершения важного C2 CI. Тимлид назначает исполнителя; документ сам по себе не означает, что задача кому-то отправлена.

**NO-GO на внедрение:** нет истинного русскоязычного преимущества, критическая потеря на 3–4 спикерах/overlap, лицензия не разрешает запланированное использование, OOM/слишком медленно, нет работающего пути к ARM64. Даже при NO-GO исходные измерения сохраняются.

**GO на следующий эксперимент:** один or оба joint кандидата проходят frozen quality gate и имеют правдоподобный проверенный Android порт; затем отдельная ветка и полноценная приёмка с C0 fallback.
