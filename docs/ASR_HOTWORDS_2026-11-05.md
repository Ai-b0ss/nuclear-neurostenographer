# Hotwords (подсказки по контексту) для GigaAM v3 e2e RNN-T (A3): прототип и замер

**Дата:** 05.11.2026. **Статус:** замер на ПК выполнен. **Решение: NO-GO для автоматических hotwords в приложении сейчас.** Приложение, APK и рантайм телефона не менялись.

Это эксперимент B1 из [CONTEXTUAL_ASR_DECISION_2026-11-04.md](CONTEXTUAL_ASR_DECISION_2026-11-04.md). Модель и корпус те же, что в [ASR_RESEARCH_20261104.md](ASR_RESEARCH_20261104.md).

## Что нужно, чтобы hotwords вообще работали

- В приложении закреплён sherpa-onnx **1.12.20** (17.12.2025), декодирование `greedy_search`. Hotwords работают только с `modified_beam_search`. Для NeMo-трансдьюсеров (наш GigaAM RNN-T) он появился в k2-fsa/sherpa-onnx#3077 (влит 05.02.2026, релизы ≥ v1.12.24). **На телефоне сейчас hotwords недоступны в принципе**, нужно обновлять AAR.
- В `tokens.txt` GigaAM e2e (1024 куска SentencePiece) нет оценок кусков, а sherpa-onnx для разбиения подсказок требует `bpe.vocab`. Его генерирует `tools/asr_hotwords/common.py`: все оценки 0, то есть берётся разбиение с наименьшим числом кусков. Это приближение настоящего SentencePiece.
- Стенд: ПК (Xeon E5-2690 v4), sherpa-onnx 2.0.1 (Python), 4 потока, `max_active_paths=4`. Модель — A3 с хоста (SHA-256 энкодера `2cac62d0…10f1`, исходный int8 без strip opset; на ПК тексты совпадают с исправленным, см. ASR_RESEARCH).

## Данные и условия

- **Podlodka**: DEV 30 клипов (эпизоды 7/200/312/338/358) и HOLDOUT 20 клипов (132/275/292/306). Это ручная расшифровка IT-подкаста, клип декодируется целиком. Лицензия не указана: только оценка, тексты не коммитятся.
- **Термины** (`terms.py`) — латиница и слова с заглавной не в начале предложения, взятые из эталона: Ruby, Python, observability, Librispeech, OpenSTT, Егор, Хабре… Всего **31 вхождение на DEV и 16 на HOLDOUT**, в 19 клипах из 50. Выборка маленькая.
- Условия:
  - `greedy` — как в приложении;
  - `beam` — beam search без подсказок;
  - `oracle` — подсказки = термины этого клипа в той форме, как они сказаны. Это **верхняя граница**: пользователь заранее знает все слова;
  - `oracle-cyr` — только кириллические термины (имена);
  - `distractor` — термины клипа из другого эпизода, которые в этом клипе **не произносились**. Проверяет ложные вставки.
- Метрики (`score.py`):
  - WER по проектной нормализации;
  - **TER** — доля вхождений терминов эталона, не совпавших при выравнивании;
  - вставки слов-подсказок, которых нет в эталоне;
  - **обрезанные гипотезы** — слов < 70% от `beam`;
  - парный bootstrap ΔWER к `beam` по клипам (10 000 повторов, 95% ДИ).

### Что видно

1. **Подсказки работают, но окно полезного веса узкое.** При score ≤ 1,5 почти ничего не меняется. При 2,0 TER на HOLDOUT падает с 9/16 до 7/16 и WER с 8,33% до 7,90% (ДИ включает 0). Но на DEV тот же вес ухудшает WER (+1,2 п.п., ДИ [−0,36; +4,21]): вес, выбранный на DEV, не переносится.
2. **Главный риск — тихая потеря текста.** На `podlodka-train-10` (oracle 2,0) модель вывела «Haskel…» и **оборвала остаток клипа**: 34 слова вместо 56, +20 ошибок, без какого-либо признака сбоя. Это похоже на известную проблему beam search у NeMo-трансдьюсеров (k2-fsa/sherpa-onnx#3267). При score ≥ 3 появляются мусорные латинские вставки («Ruby come com deson come come», «Wav Wav Veche Vech») и обрывы.
3. **Почти все ошибки на терминах — английские слова, сказанные по-русски**: observability, Librispeech, Fortran, AlphaZero, Skyeng, opcode. Модель пишет их кириллицей (например, «джаваскрипторам»). Латинская подсказка режется на однобуквенные куски, отсюда и неустойчивость. Кириллические имена (Егор, Даня Пилин, Салахутдинов) A3 и так распознаёт; `oracle-cyr` ничего не даёт.
4. **Ложные подсказки при score ≤ 2 не вставляются** (0 вставок), но немного повышают WER на DEV (до +0,5 п.п., ДИ [0,0; +1,1]).
5. На синтетике `syn3-clean` (5/52 на телефоне) все 5 ошибок — **повторы на стыках окон** («Я недоволен Яндекс. Я недоволен Яндекс Маркетом», «Скажи. Скажи мне», «Играй, играй»), а не термины. Hotwords их не исправят: это задача нарезки окон, см. сессию «ASR без нарезки на смене говорящих».

## Решение

| Вариант | Решение | Почему |
|---|---|---|
| Hotwords (B1) в приложении автоматически | **NO-GO сейчас** | Выигрыш только на верхней границе (oracle) и только при одном весе; вес не переносится с DEV на HOLDOUT; риск тихого обрыва текста; +35% к времени ASR; требует обновить закреплённый рантайм |
| Beam search без подсказок | NO-GO | WER = greedy, дороже на 35% |
| Обновление sherpa-onnx ради hotwords | не оправдано этими данными | Отдельная работа с риском (AAR, `verifySherpaRuntime`, проверки в `tools/runtime`); вернуться, если появится более устойчивая версия и корпус побольше |
| **B0: обратимый словарь написаний** («джаваскрипт» → JavaScript, «хабре» → Хабре) после ASR | **Следующий шаг (рекомендуется)** | Основная ошибка — кириллическое написание английских терминов. Словарь не трогает декодер, не может оборвать текст, показывается как «было → стало», включается пользователем |
| Повтор на стыках окон | отдельная задача | Это основной источник ошибок на диалогах |

## Ограничения

- 47 вхождений терминов — мало. ДИ по WER широкие, TER на HOLDOUT считается по 16 вхождениям.
- Подсказки oracle взяты из эталона в той форме, как сказано. В жизни пользователь пишет начальную форму («Хабр»), поэтому реальный эффект скорее ниже.
- `bpe.vocab` с нулевыми оценками — приближение. С настоящими оценками SentencePiece (их нет в публичном экспорте) результат мог бы отличаться.
- ПК, не телефон. Один прогон на условие. Клипы до 59 с декодировались целиком, а не окнами приложения. Проверялся только `max_active_paths=4`.

## Воспроизведение

```bash
python -I tools/asr_hotwords/run.py K:/nn-asr-models/A3 K:/nn-asr-data/corpus RESULTS/beam.json beam
python -I tools/asr_hotwords/run.py K:/nn-asr-models/A3 K:/nn-asr-data/corpus RESULTS/oracle-2.json oracle 2
python -I tools/asr_hotwords/score.py K:/nn-asr-data/corpus RESULTS score.json
```

Конфигурации: `greedy`, `beam`, `oracle`, `oracle-cyr`, `distractor`, вес — последний аргумент. Нужен sherpa-onnx ≥ 1.12.24 (замер: 2.0.1). Корпус готовит `tools/asr_20261104/prep_podlodka.py`.
