# Nuclear IT Hack: официальный JSON для жюри (06.11.2026)

Источник: предоставленный командой скриншот слайда «Формат JSON-вывода».
На слайде задана точная структура:
```json
{"transcript":[{"speaker_id":"speaker_1","start_ms":1250,"end_ms":4380,"text":"Добрый день!"}]}
```

В приложении кнопка **JSON для жюри** создаёт \`*.contest.json\` с единственным корневым полем \`transcript\`; каждая запись содержит ровно \`speaker_id\` (string), \`start_ms\` (integer), \`end_ms\` (integer) и \`text\` (string). Миллисекунды отсчитываются от начала аудио. Идентификаторы \`speaker_1\`, \`speaker_2\` и т.д. назначаются по порядку первого появления исходного кластера; они постоянны внутри одного экспорта, но не между записями.

Экспорт для жюри использует **исходный ASR-текст** и не применяет принятые пользователем исправления терминов: незаявленные подстановки и удаления влияют на WER. Обычная кнопка JSON по-прежнему сохраняет расширенный формат для диагностики и восстановления с \`segments\`, предупреждениями и provenance. TXT/SRT не изменены.

**Неоднозначность официальной схемы:** пример не описывает случаи, когда диаризация не установила говорящего. Чтобы сохранить тип \`string\` и не выдумывать человека, используется \`"unknown"\`. Требуется уточнить у организаторов, принимает ли их парсер такую строку; запрещено объявлять это подтверждённым контрактом.

Проверка: \`python3 tools/verify_contest_json.py core/build/export-samples/contest/dialogue.json core/build/export-samples/plain/dialogue.json\`. Скрипт валидирует строгие ключи, типы, порядок, сохранность слов и интервалов относительно расширенного исходного экспорта. Тесты не доказывают качество ASR/DER или совместимость с неизвестным парсером организаторов. До установки на телефон необходимо проверить реальный Android CreateDocument и распарсить сохранённый файл.
