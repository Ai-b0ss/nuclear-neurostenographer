# C0 против Nemotron 3 Diarization: host-бенчмарк для issue #7

**Дата:** 3 ноября 2026. **Среда:** Windows x86-64, Xeon E5-2690 v4, 2 потока инференса. **Физический ARM64: NOT_RUN** (телефона и `adb` на этой машине нет), поэтому ниже нет ни одной цифры скорости или памяти телефона.

## Вердикт

- **Android-прототип C2 (Nemotron INT8): GO**, в отдельной ветке.
- **Замена C0 в конкурсной сборке: пока NO-GO.** Условие снятия: тот же сценарий на физическом ARM64, 5 запусков подряд в авиарежиме, измеренные RTF и суммарный PSS, без регрессии записи, импорта и экспорта.
- **C2 вместо C1:** разница качества между ними мала, а INT8 расходует заметно меньше памяти на ПК.

## Что сравнивалось

ASR для cpWER один: GigaAM v3 CTC с теми же окнами и слиянием из кода приложения. Ревизии и SHA-256: [pins.json](evidence/diarization-c0-c1/pins.json). Правила отбора записаны в [build_corpus.py](../tools/diar_bench/build_corpus.py) до запуска моделей, хеши всех 87 записей (102,8 минуты): [corpus-manifest.json](evidence/diarization-c0-c1/corpus-manifest.json). Аудио и эталоны в Git не входят.

## Проверки устойчивости вывода

- **Порог C0.** Подбор на тех же файлах может только приукрасить C0. Лучшее на DataHive: 18,52% при 0,95, на ru-book: 17,92% при 0,85. Оба хуже C2 (6,33% и 7,84%). Порог 0,9 ранее сливал голоса на актёрской пробе. Единого порога, закрывающего разрыв, нет.
- **Другой эталон DataHive.** С энергетическим VAD вместо Silero: C0 34,30%, C1 15,20%, C2 15,21%. Абсолютные значения зависят от эталона, порядок систем и разрыв по confusion (22,12 против 0,56) сохраняются. [sensitivity.json](evidence/diarization-c0-c1/sensitivity.json).
- **Скорер.** На 10 записях DER `score_transcript.py` совпал с pyannote.metrics с точностью до 5 знаков. MeetEval для cpWER не сверялся.

## Найденные сбои и препятствия

- **ORT 1.17.1 (приложение) не загружает экспорт как есть:** `Unsupported model IR version: 10`. После смены объявленной IR на 9 падает `preprocessor_core.onnx` на узле STFT. Сам энкодер на 1.17.1 работает, если мел-спектрограмму посчитать отдельно: fp32 совпал с 1.31.1 побайтно на одном файле, INT8 отличается от него на 0,07% DER. Значит, нужен свой мел на Kotlin или C++ либо другой рантайм.
- **C0 один раз упал в нативном коде:** `EXCEPTION_ACCESS_VIOLATION` в `sherpa-onnx-jni.dll`, порог 0,95, `rubook-rec_0143`. Это исследовательский порог и upstream JNI для Windows без Android-патча из репозитория. На пороге 0,8 падений нет.
- **Слабые места Nemotron:** `ru_000001` даёт 49% DER и 3 кластера вместо 2 у C1 и C2. При шуме 0 дБ confusion около 10% и точное число спикеров только в 6 файлах из 8. На естественных звонках 40% времени перекрытий не находится.
- **Больше слов без спикера у C1 и C2 на ivkond:** 15–16% против 9% у C0, потому что Nemotron чаще отмечает перекрытие. Восстановления текста внутри перекрытий нет.

## Ограничения

- **Эталон DataHive получен VAD по отдельным каналам, человек его не проверял.** Это двое собеседников, созвоны, MP3. Естественной речи 3–4 человек и записи в комнате на телефон в бенчмарке нет.
- **ru-book синтетический:** смесь аудиокниг, RTTM генератора учитывает внутренние паузы как речь. Голоса повторяются между файлами.
- **ivkond: DER не считается в таблицах.** Разметка покрывает около 100% времени при примерно 45% активных кадров. `comparison-ivkond.json` формально выходит с кодом 0 и содержит эти DER, использовать их нельзя. Текстовые метки независимо не проверены, voice origin не описан.
- **Независимость от обучения неизвестна.** Какие голоса видели модели при обучении, я не проверял.
- **C0 на Windows без нативного патча Android-сборки**, а значит, его сбои не обязательно повторятся на телефоне. Результат C1 и C2 зависит от стороннего экспорта и Python-цикла, это ещё не код приложения.
- **LiteRT не запускался.** Его цифры в карточках остаются заявлениями авторов.
- **Инструмент PR #11** помечает время как сравнимое, потому что описание среды совпадает. Версии ORT различаются, см. выше.

## Что делать на Android

Порядок ниже: гипотеза о стоимости, он ещё не проверен запуском.

1. Сначала замерить текущий C0 на ARM64: это нулевая точка.
2. Прототип в изолированном `:diarization`-процессе: взять Kotlin-код мел-спектрограммы и кэша из [LiteRT-образца](https://huggingface.co/litert-community/Nemotron-3-Diarization-LiteRT), сверить результат с C2 на этих же файлах.
3. Если LiteRT не подойдёт, собрать sherpa-onnx из [PR #4119](https://github.com/k2-fsa/sherpa-onnx/pull/4119) по уже существующему CI без TTS.
4. Критерии GO для замены: DER на тех же файлах не хуже C2 более чем на 1 п.п., 5/5 запусков, устойчивый RTF ≤0,5 на POCO или другом среднем телефоне, суммарный PSS и размер приемлемы, лицензия OpenMDW-1.1 и NOTICE в APK.
5. Контрольные записи команды с согласия: финальная проверка, пока не сделана.

## Как воспроизвести

Нужны Python 3.13, ffmpeg, JRE 17, `pip install onnxruntime numpy soundfile psutil pyarrow onnx pyannote.metrics`. Скачайте файлы из `pins.json` в `ROOT/data/models/{c0,asr,nemotron,silero}` и `ROOT/data/raw/{rubook,ivkond,datahive}` (shard 0 ivkond сохранить как `shard0.parquet`). Актёрский клип: `python tools/provision_dialogue_benchmark.py`.

```bash
python tools/diar_bench/build_harness.py --root ROOT --java JAVA17
```

```bash
python tools/diar_bench/build_corpus.py --data ROOT/data --evidence docs/evidence/diarization-c0-c1 --acted ACTED_DIR
```

```bash
python tools/diar_bench/run_bench.py --root ROOT --java JAVA17 --ort-python PY --manifest docs/evidence/diarization-c0-c1/corpus-manifest.json --evidence docs/evidence/diarization-c0-c1
```

```bash
python tools/diar_bench/score_bench.py --root ROOT --evidence docs/evidence/diarization-c0-c1
```

```bash
python tools/diar_bench/sensitivity.py --root ROOT --evidence docs/evidence/diarization-c0-c1
```

Порог C0 и замер на 20 минутах запускаются через `run_bench.py` с `--c0-threshold`, `--repeat-suffix=-t085` или `--manifest long-manifest.json --corpus ...`. Хеши WAV сверяются перед каждым запуском: несовпадение останавливает прогон. Сверка `run_c1.py` с ORT 1.17.1: `check_ort117.py` и `check_ort117_encoder.py`.
