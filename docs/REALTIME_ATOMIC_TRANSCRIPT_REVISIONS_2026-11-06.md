# Атомарное сохранение версий стенограммы — испытано на Android ARM64

Дата: 6 ноября 2026. Ветка: `feature/realtime-honor-20261105`.
Базовый локальный чекпоинт: `96b845f`. Репозиторий остаётся в **существующем checkout**, без push/merge.

## Исходный риск и устранённая причина

Ранее `RealtimeSession.publish()` по отдельности вызывал сохранение:
1. `transcript.json`;
2. `transcript.txt`;
3. `transcript.srt`.

Каждый файл переименовывался атомарно, но тройка **не являлась атомарной транзакцией**. Если процесс падал между переименованиями, внешнее приложение могло увидеть три разных версии стенограммы, даже если все три файла существовали.

Теперь `core/.../TranscriptSnapshotStore.kt` реализует запись по принципу **immutable snapshot + atomic commit pointer**:

1. Внутри собственной приватной папки `realtime/<session>/transcript-versions/` создаётся новый временный каталог `.pending-vNNNNNNNNNN`.
2. JSON, TXT, SRT записываются в него с `FileDescriptor.sync()`; каждому файлу рассчитывается SHA-256.
3. `snapshot.json` содержит номер ревизии, состояние `PROVISIONAL|FINAL`, длительность и SHA-256 трёх файлов.
4. Каталог целиком переименовывается в `vNNNNNNNNNN`.
5. `transcript-current.json` публикуется **одним атомарным переименованием** с номером, статусом, длительностью и SHA-256 `snapshot.json`.
6. Только после коммита обновляются традиционные `transcript.json`, `.txt`, `.srt`. Это **зеркала совместимости**, а не атомарный набор: при сбое могут быть разной ревизии. Надёжные читатели должны брать `transcript-current.json` и проверять целостность канонического набора.

При сбое до шага 5 актуальной остаётся старая версия. При сбое после шага 5 каноническая новая версия уже полностью записана и проверяема; даже если зеркала не успели обновиться, указатель ссылается на целый набор.

Числа ревизий учитывают в том числе оставшиеся `.pending` каталоги после рестарта (без пересечения имён). После успешной публикации оставляются последние **3** версии. WAV и файлы предыдущих сессий не затрагиваются. Сбой проверки целостности ведёт к ошибке, а не к молчаливому использованию повреждённых данных.

- Номер финальной канонической ревизии: **33**, статус `FINAL`, `audio_ms=60000`.
- SHA-256 `snapshot.json` и трёх канонических файлов сверены **независимо после чтения через ADB**; они побайтно совпали с зеркальными экспортами JSON/TXT/SRT. `tools/realtime/verify_device_snapshot.py` сохраняет только тестовую публичную запись с проверенным `invocation`.
- Независимый RTTM-скорер: **DER 5,1701225%**, тот же результат, что прежний исходный аппаратный прогон на этой записи; 2/2 говорящих. Compute RTF: **1,0127** — меньше прежних ~1,030, но одиночное измерение не доказывает ускорение.
- Полный wall time инструментального сеанса ~**89,4 с**, а не 60 секунд; пользовательскую задержку нельзя отождествлять с compute RTF.

Доказательства: `docs/evidence/snapshot-phone-20261106/snapshot-default-2voice/` с `transcript-current.json`, `transcript-versioned/snapshot.json`, тремя каноническими документами и `snapshot-verification.json`.

Отдельная **device-only** `RealtimeDeviceTest#transcriptSnapshotCrashRecovery`:

- Восемь точек искусственного прерывания, **8/8 PASS**, реальная приватная Android файловая система и вызовы `fd.sync`/`Files.move(ATOMIC_MOVE)`;
- После каждого сбоя вновь созданный `TranscriptSnapshotStore` выбирает корректную ревизию, а новая публикация не перезаписывает предыдущую;
- **128 последовательных публикаций**, максимум **3 завершённых канонических версии**;
- Статус `PASS`, без доступа к микрофону и моделям, wall ~**11,2 с**.

Доказательства: `docs/evidence/snapshot-phone-20261106/snapshot-crash-injection/realtime-snapshot-recovery.json`.

## Дополнительная проверка и ограничения

Проверка `phone.py` теперь для **успешных публичных инструментальных аудиотестов** проверяет pointer, SHA-256 snapshot, SHA-256 каждого формата и совпадение с зеркалами, прежде чем сохранить evidence. Чужие данные и пользовательские личные записи не извлекаются.

**Что доказано:** атомарная *видимость* согласованного набора с устройством, устойчивость к искусственным исключениям/прерыванию записи на уровне программного кода, проверяемые хэши и ограничение числа версий.

**Что не доказано:** абсолютная долговечность после аппаратного отказа питания посреди системного `rename` (родительские каталоги не `fsync`); эквивалентность искусственного exception реальному `SIGKILL` на каждом шаге; полноценная часовая запись с живым микрофоном + ASR + C2 + экспорт; нулевое влияние на p95 latency/энергию при многочасовом непрерывном распознавании. Прошлые hour-journal тесты не следует представлять как часовой Android end-to-end.

Существующие флаги `consensusExperimental=false` и `c2Chunk72AfterThreeExperimental=false` **не менялись**. Оптимизация скорости остаётся NO-GO из-за воспроизводимой регрессии DER на Veche3.
